## 2026-09-23 — Design and accessibility pass over Phase 2 screens (Execution Plan step 2.6, closes Phase 2)

**What**: Ran `design:design-critique` then `design:accessibility-review` over every screen added in steps 2.1–2.5 (goals, journal, streak badge, reminder settings), per the skill invocations CLAUDE.md rule 5 calls for. Grounded the review in real artifacts rather than reading code alone: seeded representative data (active + achieved goals, prompted + freeform journal entries, a multi-day playback-session streak) via the debug console against the local Supabase stack, screenshotted every screen in both dark and light mode (`resize_window`'s `colorScheme` emulation), and computed WCAG relative-luminance contrast ratios for every accent-color-as-text pairing rather than eyeballing it.

Found that `secondary` (violet, journal prompts) and `success` (green, goal "Achieved" badge/toggle) are single flat hex values shared identically between light and dark mode — fine for the neutrals (`background`/`surface`/`textPrimary`/etc., which already are mode-aware), but a single accent hex can't hit 4.5:1 against both a near-black and a near-white background. Journal prompt text measured 3.33:1 in dark mode (fails); the Achieved badge measured 2.60:1 in light mode (fails). Fixed both, but differently, based on blast radius: `success` has zero other usages in the app, so it was safe to make directly mode-aware (now 4.94:1 in light mode, unchanged 6.96:1 in dark). `secondary` is also `TrimEditor`'s Phase-1 save-button fill color, which already has good contrast and didn't need changing — rather than risk an unrelated visual shift to an already-shipped, already-screenshotted Phase 1 component, added a new `accentText` token instead (5.11:1 in dark mode; light mode reuses the original violet, which was already AA-safe there at 5.44:1) and pointed only the three journal-prompt call sites at it.

Also fixed, all newly introduced this phase and cheap: several bare-text `Pressable`s (Replace/Remove image, Write freeform instead, Use today's prompt instead) had no padding at all, so their actual touch target was just the text's own bounding box — almost certainly under NFR-401's 44×44pt minimum on a real device. Added `hitSlop={8}` to each. The three new `Image` elements (goal thumbnails — the first user-content images anywhere in this app) had no `accessibilityLabel`; added one to each.

Found several more real issues but deliberately left them undone, each for the same reason — they're systemic across every phase of the app, not introduced by or scoped to Phase 2, and fixing them now would be a much larger cross-cutting change than "a design pass over Phase 2 screens" calls for: `primary` (gold) fails AA as text/button-fill-partner in light mode (~2.2:1) but is the fill color for nearly every button since Phase 0 (Sign in, Record, Save, Add goal, …); `error` fails AA as caption-size validation text in light mode (~3.2:1), same story since `record.tsx`/`auth.tsx`; no `TextInput` anywhere in the app has an explicit `accessibilityLabel` (relies on `placeholder`, a real but pre-existing gap, not a Phase 2 one); no screen's own title uses `accessibilityRole="header"` — adding it only to `goals.tsx`'s two new section headers while every other screen's H1 lacks it would be a worse, inconsistent half-fix, not a real one. All of this is exactly what NFR-402 already gates to the full step 5.3 audit before Phase 5 — documented here (and in `constants/theme.ts`'s own comment) so it isn't lost between now and then.

**Why**: Execution Plan step 2.6, the last step in Phase 2 (exit criteria: goals + streaks + journaling all work — now true, and now checked for real usability/accessibility issues rather than just functional correctness). The fix-vs-defer split follows directly from blast radius and whether an issue was actually introduced by Phase 2's own new code, not from any external instruction — flagging the reasoning here rather than silently fixing everything (which risks unreviewed collateral changes to already-shipped screens) or silently fixing nothing (which wastes a real, cheap opportunity to catch issues before they compound).

**Verification**: No behavioral/logic changes — a token- and attribute-level pass — so the existing 191/191 test suite continuing to pass (unchanged) is the right signal, alongside a clean typecheck/lint. The real verification was empirical: computed each contrast ratio via the actual WCAG relative-luminance formula (not an approximation) before picking a replacement value, confirmed every fixed pairing clears 4.5:1 with margin, then re-screenshotted the journal list/goals list in both dark and light mode against the local Supabase stack to confirm the fixes are visually correct and nothing else regressed. Test data cleaned up from the local stack afterward (goals and journal entries deleted via the debug console and confirmed synced); the local Supabase stack was stopped since this step needed no migration.

## 2026-09-23 — Daily reminder notifications, opt-in/opt-out (Execution Plan step 2.5)

**What**: New `lib/reminders.ts` wraps `expo-notifications` for a single daily local reminder. `enableReminder(hour, minute)` checks current permission, only prompts if not already decided (mirrors the mic/photo-library permission convention from earlier steps — never re-nags after a decline that can't be re-asked), cancels whatever was previously scheduled (by its own returned identifier, not `cancelAllScheduledNotificationsAsync` — surgical in case another notification type is ever added), then schedules a `DAILY`-type trigger (a first-class trigger type in this SDK version — `{ type: SchedulableTriggerInputTypes.DAILY, hour, minute }` — simpler and clearer than assembling a repeating calendar trigger by hand). `disableReminder()` cancels it. State (enabled, hour, minute, plus the notification's own identifier, needed later purely for cancellation) lives in AsyncStorage only — deliberately no Postgres table, no sync queue entry, matching SYSTEM_DESIGN.md's explicit scoping of this feature to "on-device scheduling, no server round trip." A scheduled local notification only exists on the device that scheduled it regardless of what's synced, so a synced "enabled" flag alone wouldn't actually reschedule anything on a new device — syncing would need its own re-scheduling trigger on app launch to be meaningful, which is more machinery than a single-device v1 feature warrants.

Settings screen gains a "Daily reminder" card: a `Switch` for opt-in/opt-out (FR-701/FR-702) and, once on, a row of half-hour preset time chips (8:00 PM–11:00 PM) — reused the sleep-timer chip UI pattern from the Player screen rather than pulling in a native time-picker dependency for exactly one input across the whole app. Added the `expo-notifications` config plugin to `app.json` with no custom options (no notification icon/sound assets exist yet beyond the placeholder app icons).

**Why**: Execution Plan step 2.5, the last item before Phase 2's design/accessibility pass (step 2.6). The AsyncStorage-only (not synced) storage decision follows directly from what SYSTEM_DESIGN.md already specified for this feature, rather than defaulting to the local-first-plus-sync-queue pattern used everywhere else in this app — worth calling out since it's the first entity in Phase 2 that deliberately *doesn't* get that treatment, and the reasoning (a schedule is inherently per-device) is why.

**Verification**: 191/191 tests passing (up from 175) — `reminders.test.ts` covers the granted/needs-permission/denied/cannot-re-ask paths, confirms a failed `enableReminder` call persists nothing (so the UI can't end up claiming "enabled" when it isn't), confirms the previous notification is cancelled by identifier before a reschedule, and covers `formatReminderTime`'s midnight/noon edge cases; `settings.test.tsx` gained coverage of the toggle-on/toggle-off/permission-denied/reschedule-on-time-change flows. Typecheck and lint clean.

No migration this step (by design, per the above), so no local-Supabase-stack pass was needed for schema/RLS — instead did a manual pass in the browser preview signed in against the local stack (to avoid creating a throwaway account on the live project for a feature that touches no database at all). ## 2026-09-23 — Journal entries: prompted + freeform, chronological view (Execution Plan step 2.4)

**What**: Migration adds `journal_entries` with `select`/`insert`/`delete` RLS for the owner, deliberately no `update` policy — same immutable-record philosophy as `playback_sessions` (step 2.3), though for a different reason: there's no edit UI planned, and a journal's value as a dated record of what you actually thought on a given night is arguably weakened by silently-rewritable history. Delete is still allowed, unlike `playback_sessions`' fully append-only design — removing your own private writing is a reasonable thing to want, editing it after the fact to say something different is a different thing. Local-first (SQLite + sync queue), matching every other entity in the app now — journaling before sleep is exactly the kind of thing that happens with no connectivity.

New `lib/journalPrompts.ts` is a small static list (12 prompts) with a deterministic local-calendar-day picker — same day, same prompt; changes at local midnight, cycles through the list. No AI involved: Phase 2's exit criteria explicitly says the manifestation loop works "without AI involvement yet," and goal-to-affirmation AI drafting (a separate, later feature) doesn't extend to journal prompts. `lib/journal.local.ts` mirrors the by-now-established local-first CRUD pattern (create/list/get/delete, no update to go with it). `app/(tabs)/journal.tsx` lists entries newest-first, showing the prompt in italic when one exists and just the body when freeform. `app/journal/new.tsx` shows today's prompt by default with a "write freeform instead" toggle (and back), rather than forcing a choice up front. `app/journal/[id].tsx` is read-only (matching the no-edit decision) with delete, following the same `Alert.alert`-confirm pattern as folders/goals/recordings.

Also added `lib/format.ts`'s `formatDate`, needed for the journal list/detail views — and pinned its locale to `'en-US'` explicitly rather than leaving it `undefined` (device default). This wasn't a stylistic choice: writing the first version of this feature's tests surfaced that this sandbox's default timezone renders dates well outside UTC (a UTC-noon timestamp displayed as the *next* calendar day locally, and `toLocaleDateString(undefined, ...)` rendered as "23 Sept 2026" rather than "Sep 23, 2026"). Pinning the locale makes the format itself deterministic across devices; the timezone behavior itself is correct and left alone (a date should display in the viewer's own local day) — but it meant several new test fixtures across this session needed to be built from local `Date` components rather than fixed UTC-literal strings to stay timezone-independent, which `lib/streak.ts`'s tests from the previous step had already (correctly) been doing.

**Why**: Execution Plan step 2.4 (FR-603–FR-604), the last "no AI" item before Phase 2's exit criteria are met. The no-update/allow-delete RLS split, the local-first choice, and the freeform-by-default-but-prompt-visible UI flow were judgment calls not spelled out in SRS/PRD beyond FR-603's one sentence — each reasoned through and documented here rather than just decided silently, per CLAUDE.md rule 6.

## 2026-09-23 — Playback session logging and streak display (Execution Plan step 2.3)

**What**: Migration adds `playback_sessions` — deliberately append-only: only `select`/`insert` RLS policies exist, no `update`/`delete` at all, not even for the row's own owner. Streaks are derived from this log, so its integrity shouldn't depend on trusting the client not to rewrite history after the fact; this is stricter than every other table in the project so far (folders/affirmations/goals all allow the owner to update/delete their own rows). `lib/db.ts`/`lib/syncQueue.ts` gained the table; new `lib/playbackSessions.local.ts` logs a session through the same local-first write-then-enqueue pattern as everything else — worth calling out specifically here since a nightly playback session is arguably the single most likely piece of app data to be created with zero connectivity (phone asleep, no wifi), making local-first non-negotiable rather than just consistent.

New `lib/streak.ts` is a pure function over a list of `played_at` timestamps: converts each to a **local** calendar-day key (not UTC — a streak is about the user's own days), then walks backward from today counting consecutive days. A session logged but not yet reflected as "today" doesn't reset the streak to 0 — if yesterday has a session but today doesn't yet, the streak is still shown as of yesterday's count, only actually resetting once a full calendar day is skipped entirely (matches how every mainstream streak feature already behaves; the alternative — resetting at the stroke of midnight before that night's session is even logged — would be a worse, more punishing product decision nobody asked for). A small 3-tier emoji (🌱/🌿/🌳) gives FR-602's "visual growth metaphor" without needing any illustration assets, which don't exist yet beyond placeholder app icons.

`app/(tabs)/player.tsx`'s `handleStop` — already the single code path for both a manual Stop press and sleep-timer expiry — now also logs the session there, using a `sessionStartRef` captured in `handleStart` so `played_at` is the session's *start* time, not its end time (a session spanning midnight belongs to the night it started, not whatever day it happened to end on). New `components/StreakBadge.tsx` surfaces the streak on the Library tab's header — the app's home screen, and the most natural "reinforcement loop" touchpoint per PRD's framing, though no screen was mandated by SRS/PRD for this.

**Why**: Execution Plan step 2.3 (FR-601–FR-602). The append-only RLS design, the local-first requirement, and the "streak stays alive on yesterday" semantics were all judgment calls not spelled out anywhere in SRS/PRD/SYSTEM_DESIGN beyond the one-sentence FR text — each is documented here with its reasoning rather than silently decided, per CLAUDE.md rule 6 (senior-engineer judgment, but the reasoning behind it should be legible, not just the outcome).

## 2026-09-23 — Goals schema, local-first data layer, and image sync (Execution Plan step 2.1, part 1 of 2)

**What**: Start of Phase 2. Split step 2.1 ("goals schema + vision board CRUD UI") into two commits — this one covers the schema and data layer; the vision board UI itself follows separately. New migration [20260923090000_create_goals.sql](supabase/migrations/20260923090000_create_goals.sql) adds `goals` (RLS on all four ops, matching the folders/affirmations pattern) with a two-way check constraint (`(status = 'achieved') = (achieved_at is not null)`) so an achieved goal always carries a timestamp and an active one never does — enforced in Postgres, not just the client. Also adds a `goal-images` Storage bucket (the project's first) with owner-only RLS policies keyed on `(storage.foldername(name))[1] = auth.uid()`. Unlike audio recordings' opt-in cloud backup (ADR-0004, a privacy decision specific to voice data), goal images upload automatically — that rationale doesn't carry over to a vision-board image the user already chose to add.

`lib/db.ts`'s SQLite schema and `lib/syncQueue.ts`'s `SyncTable` union both gain `goals`. New [lib/goals.local.ts](lib/goals.local.ts) mirrors `folders.local.ts`/`affirmations.local.ts`'s local-first conventions (write locally, always succeeds offline; enqueue the Postgres op) for create/list/get/update-text/update-status/update-image/delete. The Storage upload itself can't go through the generic sync queue (it only knows how to replay Postgres table rows), so new [lib/goalImages.ts](lib/goalImages.ts) handles it separately: `uploadPendingGoalImages()` scans for goals with a local image but no synced `image_path`, uploads to a deterministic `{user_id}/{goal_id}` key (`upsert: true`, so a later image replacement is just an overwrite, no delete-then-upload dance), and enqueues the resulting path back. `hooks/useSyncQueue.ts` calls it after `processQueue()` on reconnect, but only when that drain fully completed — an image's path update can't sync before the goal's own row has, so if the queue stalled, image upload is skipped this round rather than firing an update against a row that may not exist remotely yet. Image removal deliberately does *not* try to delete the now-orphaned Storage object over the network (accepted as a bounded, harmless leak cleaned up when the goal or account is later deleted) — not worth a network round trip and offline-safety complication for every single removal.

`lib/account.ts`'s `deleteAccount` extended: Storage objects don't cascade-delete with the `auth.users` row the way table rows do, so goal images are explicitly listed and removed *before* the RPC call, following the same ordering principle as the RPC itself — if that removal fails (offline, error), nothing has been destroyed yet, so the whole call throws without touching anything.

**Why**: Execution Plan Phase 2, step 2.1 (FR-401–FR-404). Split into two commits because combining schema/data-layer work with UI work in one step felt too large to verify well in one sitting (CLAUDE.md rule 1's "split before starting" guidance) — this half is independently verifiable on its own, and the vision board UI can be built and reviewed against a data layer already proven correct. The local-first vs. direct-to-Supabase question, and the auto-upload vs. local-only-for-now question for images, were both real architectural forks with no obviously-correct answer from the docs alone (SYSTEM_DESIGN.md's API design section groups goals with folders/affirmations under "direct client → Supabase" but that's describing the API surface, not ruling on the local-first detail underneath it) — asked the user rather than guessing; both went with the more consistent, `Recommended` option (local-first reusing the existing generic sync-queue infra; auto-upload since the audio opt-in rationale is privacy-specific and doesn't apply here).
