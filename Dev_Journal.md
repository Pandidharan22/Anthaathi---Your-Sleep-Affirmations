## 2026-09-22 — Player: loop playback, sleep timer, background audio (Execution Plan step 1.7)

**What**: Implements FR-301 (play selected affirmations in a loop), FR-302 (sleep timer), FR-303 (continue when backgrounded/locked). [app/(tabs)/player.tsx](app/(tabs)/player.tsx) has a two-state screen: selecting (multi-select the recordings to play + choose a sleep timer of 15/30/45/60 minutes or none) and playing (current track, elapsed/duration, timer countdown, Pause/Resume, Stop). `expo-audio`'s built-in `AudioPlaylist` was considered but rejected — it has no concept of per-track trim points, and honoring step 1.5's trim feature during actual nightly playback (the entire point of building it) mattered more than the convenience. Instead, playback is driven by one `AudioPlayer` whose source swaps per track (a `playCount` counter, not the derived track index, drives re-triggering — needed because looping a *single* selected track means the index never changes, so something else has to force each loop iteration to re-fire). Advancing is driven by a real `playbackStatusUpdate` event listener (not a `useAudioPlayerStatus`-driven effect calling `setState` reactively, which the project's lint config already flags as a `react-hooks/set-state-in-effect` antipattern) checked against each track's `trim_end_ms` (or `duration_ms` if untrimmed) — wrapping back to the first track after the last via modulo. Background playback: `setAudioModeAsync({ shouldPlayInBackground: true, interruptionMode: 'doNotMix' })` plus `player.setActiveForLockScreen()` per track — the latter matters specifically because `expo-audio`'s own docs say Android background playback stops after ~3 minutes without active lock-screen controls, which would silently break the app's entire premise (an overnight session) if skipped. The native background-audio entitlements were already configured by `expo-audio`'s config plugin defaults from step 1.4, so no `app.json` change was needed here.

**Why**: Execution Plan step 1.7 — the last piece of the core self-recorded-affirmations loop (record → organize → **listen**) before Phase 1's remaining housekeeping steps (account deletion, phase review).

**Verification**: `typecheck`/`lint`/`test` all green (65 tests, 5 new for the Player covering selection→play, trim-aware advancement between two differently-trimmed tracks, loop-wrap back to the first track, Stop, and sleep-timer expiry via Jest fake timers). Manual pass via the web preview surfaced a real layout bug — the sleep-timer chip row (and, on inspection, the existing `FolderPicker` chips too) rendered stretched vertically inside a horizontal `ScrollView` on web; fixed in both by constraining the `ScrollView`'s own style (`flexGrow: 0`) alongside its `contentContainerStyle`. Confirmed the fix visually, then confirmed selection, timer-chip selection, Play correctly transitioning to the playing state with the right track/duration text, and Stop returning cleanly with the prior selection preserved — including graceful handling (no crash) when the test recording's fake file predictably fails to load in-browser. **Known gap**: the execution plan's own verify text ("playback survives lock screen on both iOS and Android test devices") needs a physical device/simulator, unavailable in this environment until Phase 5 — the background/lock-screen API usage is grounded in the library's documented requirements, not guessed, but genuinely untested on-device.

## 2026-09-22 — Trim UI for pending and saved recordings (Execution Plan step 1.5)

**What**: Implements FR-203. Added a migration adding nullable `trim_start_ms`/`trim_end_ms` to `affirmations` plus a check constraint (`trim_end_ms > trim_start_ms`, `trim_end_ms <= duration_ms`, both-or-neither null) — trim is non-destructive: the audio file is never re-encoded, playback just starts/stops at these offsets. [lib/db.ts](lib/db.ts)'s local SQLite schema got the same columns, plus a best-effort `ALTER TABLE` guard (checked via `PRAGMA table_info`) so dev databases created before this step keep working without a real migration framework, which would be premature pre-launch. [components/TrimEditor.tsx](components/TrimEditor.tsx) is a reusable play/scrub/set-start/set-end/preview/save component — scrubbing uses `@react-native-community/slider` for position only (not a dual-handle range control, avoiding a second dependency); "Set start here"/"Set end here" capture the current playback position instead. It's used in two places: inline in [app/record.tsx](app/record.tsx)'s review step (trimming before the first save) and a new [app/affirmation/[id]/trim.tsx](app/affirmation/[id]/trim.tsx) route for editing an already-saved recording — Library rows are now pressable and navigate there, per the plan's own wording ("on a saved/pending recording") covering both cases. [lib/affirmations.local.ts](lib/affirmations.local.ts) gained `getLocalAffirmation` and `updateLocalAffirmationTrim`.

**Why**: Execution Plan step 1.5 — the natural follow-up to step 1.4's record flow, and the sequence diagram in SYSTEM_DESIGN.md always described "stop, trim, confirm" as one flow.

**Verification**: `typecheck`/`lint`/`test` all green (42 tests). **Manual verification against the local Supabase stack caught a real bug that the mocked unit tests could not**: `updateLocalAffirmationTrim` originally queued a partial-payload `upsert()` (just `id`, `trim_start_ms`, `trim_end_ms`), reasoning that since the sync queue is strictly FIFO the row would already exist remotely by the time this ran. That reasoning was correct, but the mechanism was wrong — PostgREST's `INSERT ... ON CONFLICT DO UPDATE` validates NOT NULL constraints on the *proposed insert row* before it even checks for a conflict, so a partial payload fails with a NOT NULL violation on every column it omits, regardless of whether the row already exists. Caught this by actually creating a test affirmation, opening its trim screen through the real Library UI, saving, and watching `processQueue()` fail — then confirmed the exact failure mode with a direct `curl` reproduction against the local instance. Fixed by adding a genuine `update` operation to [lib/syncQueue.ts](lib/syncQueue.ts) (`supabase.from(table).update(payload).eq('id', row_id)`, distinct from `upsert`), which only ever touches the given columns. Re-verified end-to-end after the fix: the update synced correctly, and a direct `curl` PATCH with an out-of-range trim confirmed the remote check constraint independently rejects it too. Migration applied to both local and the live project (`supabase db push`) after local verification passed. `.env` restored to the live project and local stack stopped afterward.

## 2026-09-21 — Local-first data layer: SQLite + sync queue skeleton (Execution Plan step 1.3)

**What**: Implements [ADR-0004](docs/adr/0004-audio-storage-strategy.md)'s local-first storage decision. [lib/db.ts](lib/db.ts) opens an on-device `expo-sqlite` database and creates `folders`/`affirmations` tables mirroring the Postgres schema from step 1.1, plus `updated_at`/`synced_at` bookkeeping columns (local-only, never pushed), and a generic `sync_queue` table (`table_name`, `operation`, `row_id`, `payload` JSON, `created_at`). [lib/syncQueue.ts](lib/syncQueue.ts) is table-agnostic — `enqueue()` queues a change, `processQueue()` drains it FIFO against Supabase and, on the first failure, stops and leaves that item and everything after it queued rather than dropping or reordering anything. [hooks/useSyncQueue.ts](hooks/useSyncQueue.ts) subscribes to `@react-native-community/netinfo` and calls `processQueue()` on the offline→online transition, only while a session exists. [lib/folders.local.ts](lib/folders.local.ts) (`createLocalFolder`/`listLocalFolders`) is the concrete local CRUD layer used to prove the loop — the folder write always succeeds locally first, and only queues the Postgres upsert as a side effect; affirmations' local CRUD is deliberately deferred to the recording flow (step 1.4), which will reuse this same queue/DB plumbing rather than duplicating it. Added a `__DEV__`-only `lib/devTools.ts` exposing these functions on `globalThis.__anthaathiDebug`, since no UI exists yet to drive folder creation (that's step 1.6) but the loop still needed a real way to exercise it end-to-end.

**Why**: Execution Plan step 1.3. ADR-0004 requires recordings (and their metadata) to be written locally first with zero network dependency (NFR-301), with Postgres sync as a best-effort background concern — this step builds that mechanism once, generically, so steps 1.4–1.6 (recording flow, trim, folder CRUD) can all consume it rather than each inventing its own sync logic.

**Verification**: `typecheck`/`lint`/`test` all green (23 tests: `syncQueue.test.ts` covers enqueue, successful drain, delete ops, and — the important case — that a failure stops processing and leaves remaining items queued in order rather than dropped/reordered; `folders.local.test.ts` and `useSyncQueue.test.ts` cover the local CRUD and NetInfo-triggered sync wiring, all with `expo-sqlite`/`@/lib/supabase`/NetInfo mocked). ## 2026-09-21 — AI Guided Session feature: on-device voice synthesis (new ADR-0007)

**What**: Added a new v1 feature — **AI Guided Session** — affirmations narrated by a synthesized voice (male/female choice) as an alternative to Self-Recorded, generated once and cached as a local file so it fits the existing Player exactly like a recording. Researched three real implementation paths before deciding:

1. `expo-speech` (Expo's OS-TTS wrapper) — inspected its actual TypeScript API directly rather than assuming: `speak()`, `getAvailableVoicesAsync()`, `isSpeakingAsync()`, `stop()`, `pause()`, `resume()`. Live-speech-only, no file-export method anywhere. Ruled out.
2. Recording the live TTS playback through the microphone (the user's initial proposal) — ruled out on audio-quality grounds: speaker→mic round trip, possible echo-cancellation interference, device-hardware inconsistency. Not acceptable for a "calm and soothing" voice feature.
3. **Chosen**: a custom native module wrapping each platform's actual file-synthesis capability — Android's `TextToSpeech.synthesizeToFile()`, iOS's `AVSpeechSynthesizer` buffer-writing API — unified behind one Expo Module JS interface. Fully on-device, $0 forever, no network, fits the file-based Player architecture with zero special-casing.

Documented as [ADR-0007](docs/adr/0007-voice-synthesis-strategy.md), including a fourth option (self-hosted Piper/Coqui cloud TTS, what ADR-0003 had loosely assumed) as a documented fallback if the native module's engineering cost threatens the timeline.

Updated the full doc set for consistency: `PRD.md` (new feature, moved from "Could-have" to "Should-have," new risk entry, resolved the old TTS-timing open question), `SRS.md` (new FR-511–FR-516 under a new §4.6, renumbered the old §4.6/§4.7 to §4.7/§4.8, new dev-build constraint in §3.4, new external-interface row), `SYSTEM_DESIGN.md` (new component row, `source`/`voice_id`/`script_text` columns on `affirmations`, new sequence flow, updated free-tier table, new failure-mode row, new §11 revisit note), `docs/adr/README.md` (index entry), and `EXECUTION_PLAN.md` (Phase 3 expanded from one decision-point step into 7 concrete steps: 3.5 dev-client setup, 3.6/3.7 the two native wrappers, 3.8 unified interface, 3.9 schema, 3.10 client integration, 3.11 error handling).

**Why**: The user explicitly wants this as a real feature, not a maybe, and wants it genuinely on-device/free rather than cloud-hosted — consistent with the project's free-tier-first philosophy, but with real engineering cost (first native code in this project) that needed to be made explicit and deliberately accepted, not glossed over.
