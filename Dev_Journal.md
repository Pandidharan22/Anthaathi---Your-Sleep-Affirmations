## 2026-09-29 — AI Guided affirmation creation + FR-514 caching/re-synthesis logic (Execution Plan step 3.9)

**What**: Checked first, per the note left at the end of step 3.8: `affirmations`' schema (`source`, `voice_id`, `script_text`, plus the check constraint requiring the latter two when `source = 'ai_generated'`) was already fully built in step 1.1, all the way through the local SQLite mirror and sync payload. So this step's real scope was purely the caching/re-synthesis logic FR-514 actually asks for, split across two files:

`lib/aiVoice.ts` gained `synthesizeAffirmationAudio(scriptText, voiceId)` — calls the native module, then solves a gap the native module can't: Android's `TextToSpeech` API reports synthesis success/failure but never the resulting file's duration. `measureDurationMs()` loads the freshly-written file with `expo-audio`'s `createAudioPlayer` (the non-hook, imperative variant — this runs in a plain lib function, not a component) just long enough to read `status.duration` off a `playbackStatusUpdate` event, then releases the player; rejects with a clear timeout rather than hanging forever if the file never finishes loading.

`lib/affirmations.local.ts` gained two functions built on that: `createAiGuidedAffirmation` (synthesize + save as `source: 'ai_generated'`) and `updateAiGuidedAffirmationScript` — the actual FR-514 deliverable. It compares the requested `scriptText`/`voiceId` against the existing row and does nothing at all if both are unchanged (the cached file is already correct); only re-synthesizes, updates the record, and deletes the old file (only *after* the new one is safely recorded) if either actually differs. Also resets `trim_start_ms`/`trim_end_ms` to `null` on re-synthesis — a trim set against the old audio's timing has no relationship to the new file's, and could even violate the trim-range check constraint outright if the new file is shorter than the old `trim_end_ms`, a real interaction that was easy to miss and worth catching now rather than as a field bug later.

**Why**: Execution Plan step 3.9, FR-514. The "reuse unless something actually changed" framing matters for cost as much as correctness — re-synthesizing on every unrelated edit (renaming the affirmation, moving it between folders — both already have their own `updateLocalAffirmation*` functions that don't touch audio at all) would be pointless work for a feature whose whole design goal (ADR-0007) is running entirely on-device with no external cost, but still isn't free of local compute/battery cost to burn needlessly.

**Verification**: `measureDurationMs` is new async-callback-to-promise glue code that had never touched a real audio file before this step (only mocked). Wrote real tests first (`lib/aiVoice.test.ts`: happy path measuring a real-shaped status sequence, ignoring not-yet-loaded/zero-duration updates, and a fake-timers test proving the timeout path actually cleans up its subscription and player rather than leaking them) — 3 new tests, plus 5 more in `lib/affirmations.local.test.ts` covering `createAiGuidedAffirmation` and all three `updateAiGuidedAffirmationScript` branches (re-synthesize on script change, re-synthesize on voice-only change, true no-op when neither changed, throws cleanly for a missing id). But mocked tests proving the *logic* isn't the same as proving the *real* Android audio-loading callback sequence behaves the way the mocks assume — so also added a temporary real-pipeline button to `app/dev-tts-test.tsx` (`createAiGuidedAffirmation` end-to-end, no mocks) and ran it on the user's actual device: it created a real ~3-second file (matching the short test string), showed the correct measured duration, appeared in the Library tab exactly like a normal recording, and played back correctly in the chosen voice. Deliberately did *not* separately real-device-verify `updateAiGuidedAffirmationScript`'s re-synthesis path — it calls the exact same now-proven `synthesizeAffirmationAudio`, and its only new logic (the compare-and-skip branch, the UPDATE+enqueue write) follows the identical pattern already proven for real by `updateLocalAffirmationTrim`/`updateLocalAffirmationTitle` in earlier phases; a second full device pass would have re-tested already-proven code, not this step's actual new risk. 225/225 tests (8 new), typecheck, lint clean. No migration — the schema was already there.

## 2026-09-28 — Android TTS-to-file native module, first native code (Execution Plan step 3.6)

**What**: `modules/anthaathi-tts/` — this project's first native code, a local Expo Module (Kotlin) wrapping Android's `TextToSpeech.synthesizeToFile()` per ADR-0007. Scaffolded with `create-expo-module --local` (fixed a CLI quirk that nested it as `modules/modules/anthaathi-tts` — the `--local` flag already prepends `modules/`, so passing a path that also started with `modules/` double-nested it). `AnthaathiTtsModule.kt` exposes one function, `synthesizeToFile(text, outputPath) -> Promise<string>`: lazily initializes the `TextToSpeech` engine, bridges its callback-based `UtteranceProgressListener` (`onDone`/`onError`) to the Promise, and deletes the output file on failure so no partial file is ever left behind. Every Kotlin API shape used (`Module`, the `AsyncFunction` 2-arg-plus-Promise overload, `Promise.resolve`/`reject`, `CodedException`, `OnDestroy`, `appContext.reactContext`) was verified by reading the actual `expo-modules-core` source in `node_modules` first, not assumed — consistent with this project's established discipline for new/native-adjacent APIs, and especially warranted here since this machine has no Android SDK to compile against locally, so a real EAS build is the *only* way to catch a Kotlin mistake.

Caught two real bugs along the way, both before and one *during* verification:
1. **`file://` URI mismatch, caught before building.** This app's file URIs are always `file://`-prefixed (`expo-file-system`'s convention, used for every existing audio file), but `java.io.File`'s constructor expects a plain filesystem path. Passing a `file://` string straight through would have silently created a broken relative path. Fixed in the module (`resolveOutputFile`) so JS callers never need to know about this.
2. **A `.gitignore` bug that broke the first real build.** The first EAS build ("succeeded") but the installed app threw `Cannot find native module 'AnthaathiTts'` at runtime — the Kotlin code had genuinely never made it into the build. Root cause: `.gitignore` had `android/` (no leading slash) meant to exclude the root-level `expo prebuild` output, but per standard gitignore semantics an unanchored pattern matches a directory of that name at *any* depth — so it was also silently excluding `modules/anthaathi-tts/android/`, the actual Kotlin source, from git and (since EAS Build respects `.gitignore`) from the build upload. Confirmed definitively with `git status --short --ignored=matching` (showed `!! modules/anthaathi-tts/android/`) before touching anything, rather than guessing. Fixed by anchoring the three build-output patterns to the repo root (`/android/`, `/ios/`, `/.kotlin/`) — verified both halves after the fix: `modules/anthaathi-tts/android/` no longer flagged as ignored, and `git check-ignore` on a synthetic root-level `android/...` path still matched, so the original purpose of the rule is intact.

Also added a temporary, `__DEV__`-only screen (`app/dev-tts-test.tsx`, linked from a "Dev: on-device TTS test" button on Settings) to actually exercise this on a device: synthesizes a known string, shows the result path, and plays it back via `expo-audio`. Deliberately kept isolated from `settings.tsx`'s own logic/tests rather than embedding the synth+playback flow there directly — that would have dragged `expo-file-system`/`expo-audio`/the new native module into an already-tested file, needing new mocks for code that's getting deleted once step 3.10 builds the real voice-picker UI. Matches the precedent already set by `lib/devTools.ts`: temporary dev-only scaffolding doesn't get the same test-coverage bar as shipped features.

**Why**: Execution Plan step 3.6, continuing ADR-0007 now that step 3.5's dev-client pipeline works. iOS (step 3.7) is not started — per the Android-only decision already made and journaled in step 3.5, to be explicitly addressed (not silently skipped) when that step comes up.

**Verification**: Real, on the user's own device, not simulated — the only kind that matters for native code this project can't compile locally. First build attempt installed fine but the module was genuinely missing (the `.gitignore` bug above), confirmed via the actual Metro error log (`Cannot find native module 'AnthaathiTts'`) watched live through a `Monitor` filter, not assumed. After the fix, rebuilt, reinstalled, and the user confirmed directly: tapped Synthesize, got a green success message with the file path, tapped Play, and it played back correctly — a genuinely synthesized, genuinely playable WAV file, exactly the Execution Plan's stated verify criterion. (Separately noted: pressing Play a second time without re-synthesizing did nothing, because the throwaway test screen's player sits at end-of-track after finishing and needs an explicit seek-to-0 before replaying — the same bug class as the Phase 1 `TrimEditor` fix. Not fixed, since this screen is temporary and the native module itself isn't implicated.) 214/214 tests, typecheck, lint clean — no existing JS logic changed this step, only additive.

Documented as [ADR-0007](docs/adr/0007-voice-synthesis-strategy.md), including a fourth option (self-hosted Piper/Coqui cloud TTS, what ADR-0003 had loosely assumed) as a documented fallback if the native module's engineering cost threatens the timeline.
